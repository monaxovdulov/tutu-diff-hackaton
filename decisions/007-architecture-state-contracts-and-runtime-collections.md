# ADR-007 · architecture · Как передаём состояние поездки между слоями

## С чего начинается сценарий

Пользователь пишет в виджете: «Москва → Санкт-Петербург, 24 мая, хочу
подешевле». Дальше один и тот же результат проходит через несколько частей
системы:

```text
виджет → backend → TravelAgent → backend → виджет
```

Чтобы эти части не спорили о формате данных, у нас есть общий объект
`TripWidgetState`.

`TripWidgetState` — это всё, что нужно виджету для отрисовки текущего экрана:

- `request` — какой запрос сделал пользователь;
- `messages` — сообщения в диалоге;
- `routes` — найденные варианты поездки;
- `recommendation` — какой вариант советуем;
- `progressText` — что сейчас происходит;
- `phase` — на каком шаге находится экран (`searching`, `results`, `ready` и
  так далее).

TravelAgent возвращает это состояние в JSON. Backend проверяет его через Zod,
хранит последний результат и отправляет изменения в браузер через SSE.

Когда браузер получает событие, он передаёт его вместе с текущим
`TripWidgetState` в функцию `reduceTripWidgetState`. Функция собирает и
возвращает следующее состояние виджета:

```ts
nextState = reduceTripWidgetState(currentState, event);
```

Например, для события `progress.updated` reducer оставляет все данные поездки
как есть, но заменяет `progressText` и, если нужно, `phase`. Старый объект он не
меняет: Lit видит новый объект и заново отрисовывает экран.

Поэтому формат `TripWidgetState` и формат событий — это общий договор между
агентом, backend и виджетом.

## Зачем понадобилось изменение

До рефакторинга один и тот же маршрут мог выглядеть по-разному:

```ts
{ id: "cheap" }
{ id: "cheap", difference: null }
```

Для человека это почти одно и то же: сравнения пока нет. Для TypeScript, Zod и
кода нормализации это две разные формы объекта. Из-за этого в `schemas.ts`
приходилось вручную перекладывать проверенный ответ агента в доменную модель.

Ещё две проблемы:

- `TripWidgetEvent.type` был ограничен списком событий, но `payload` — данные
  события — оставался произвольным `Record<string, unknown>`. Например, событие
  `progress.updated` можно было случайно собрать без текста, а ошибку заметить
  только во время работы приложения.
- `TravelRunStore` возвращал весь внутренний `StoredTravelRun`. Код HTTP- или
  SSE-слоя мог получить доступ к actor, журналу и подписчикам и случайно изменить
  их в обход методов store.

## Что решили

### 1. У каждого DTO одна форма

DTO здесь — обычный объект, который мы передаём между слоями и можем записать в
JSON. Все его поля объявляем явно. Если ссылочного значения пока нет, передаём
`null`, а не удаляем поле:

```ts
type TripRoute = {
  id: string;
  difference: TripDifference | null;
  recommendationNote: string | null;
};
```

Массивы в публичных типах помечаем `readonly`. Это не замораживает массив во
время выполнения JavaScript, но запрещает вызывающему коду менять его через
TypeScript. Ответ агента по-прежнему проверяет Zod. После успешной проверки форма
уже совпадает с доменной, поэтому отдельный преобразователь не нужен.

### 2. Тип события определяет его payload

`TripWidgetEvent` остаётся дискриминируемым объединением (discriminated union).
Это тип, в котором TypeScript сначала смотрит на поле `type`, а затем понимает,
какие данные должны лежать в `payload`.

```ts
type TripWidgetEventPayloads = {
  "progress.updated": { text: string | null };
  "session.failed": { message: string };
};
```

Теперь reducer читает поля без `as`-cast — принудительного обещания компилятору,
что значение имеет нужный тип. Если разработчик перепутает payload, ошибку
покажет компилятор до запуска приложения.

### 3. Коллекции остаются внутри TravelRunStore

Store больше не отдаёт `StoredTravelRun` наружу. Внешний код получает только то,
что ему нужно:

- `create()` возвращает идентификатор;
- `has()` отвечает, существует ли run;
- `snapshot()` возвращает отдельный внешний объект для чтения без actor, журнала
  и подписчиков;
- `subscribe()` возвращает снимок текущей истории и функцию отписки.

Это позволяет позже заменить внутреннее устройство store, не переписывая HTTP-
и SSE-слои.

## Почему выбраны именно эти структуры

| Что нужно хранить | Структура | Почему |
| --- | --- | --- |
| Run-ы по `runId` | `Map` | Идентификаторы появляются динамически; поиск, добавление и удаление делаются по ключу. |
| SSE-подписчики | `Set` | Одна функция подписчика должна присутствовать не больше одного раза; `Set` сам обеспечивает уникальность. |
| События одного run-а | `Array` | События только добавляются в конец и читаются в исходном порядке. |
| Состояние и события на границе API | `Object` и `Array` | Они напрямую сериализуются в JSON; `Map` и `Set` напрямую не сериализуются. |

Журнал событий маленький, события только добавляются в конец и читаются по
порядку. Для такого сценария обычного `Array` достаточно.

## На какие правила опираемся

Решение следует рекомендациям навыка
[Metarhia `js-data-structures`](https://github.com/metarhia/metaskills/blob/main/skills/js-data-structures/SKILL.md).
Ниже не цитата, а короткий перевод применённых правил:

- объект с заранее известными полями подходит для DTO и JSON;
- `Map` показывает, что перед нами изменяемый реестр по ключу;
- `Set` показывает, что важна уникальность элементов;
- `Array` подходит для упорядоченной последовательности;
- внутреннее представление коллекций лучше прятать за небольшим API;
- наружу нужно отдавать отдельное представление для чтения, а не общую изменяемую
  коллекцию;
- рост долгоживущих `Map`, `Set` и журналов нужно ограничивать.

## Что ещё рассматривали

- Оставить необязательные поля в доменной модели и преобразовывать ответ агента с
  `null` в `schemas.ts`. Тогда пришлось бы поддерживать две формы одного DTO и
  вручную синхронизировать TypeScript-тип, Zod-схему и преобразователь.
- Оставить `TripWidgetEvent.payload` как `Record<string, unknown>`. Тогда union
  проверял бы только имя события. Поля payload пришлось бы по-прежнему читать
  через небезопасные cast-ы.
- Продолжать возвращать `StoredTravelRun` из store. Это проще сейчас, но связывает
  остальные слои с внутренним устройством runtime и позволяет обойти его методы.

## Последствия

- Новое поле, допускающее `null`, придётся явно заполнить во всех фабриках и
  демо-данных. Это немного больше кода, зато забытое поле сразу найдёт TypeScript.
- Неправильный payload события теперь не компилируется.
- После Zod-проверки ответ агента можно использовать напрямую.
- Внутренние структуры store можно заменить, пока сохраняется его публичный API.
- Store всё ещё хранит данные только в памяти и пока растёт без ограничения.
  Перед долгоживущим production-процессом нужно выбрать TTL — время хранения —
  или лимит записей. Также нужно решить, сколько времени поддерживать повторное
  подключение к SSE и чтение завершённых run-ов. Это будет отдельное решение.
