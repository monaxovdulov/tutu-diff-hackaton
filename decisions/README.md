## Когда читать

Не загружай все ADR перед каждой задачей. Найди и прочитай связанные решения,
если меняешь основу продукта, границы системы, ключевую технологию или рабочий
процесс либо если существующее решение выглядит намеренным, но его причина не
очевидна.

## Когда писать

Пиши ADR, только если одновременно:

1. Решение дорого или трудно отменить.
2. Без контекста будущий читатель может не понять, почему сделано именно так.
3. Были реальные альтернативы и осознанный компромисс.

Если хотя бы одного пункта нет, ADR не нужен.

## Формат

Файл называется `001-product-short-title.md`. Номер идёт по порядку, а один
основной тег показывает область решения:

- `product` — продукт и пользовательский опыт;
- `architecture` — границы и взаимодействие частей системы;
- `technology` — стек, сервисы и инфраструктура;
- `process` — долгоживущие правила работы.

```md
# ADR-001 · product · Короткое название решения

Контекст, принятое решение и причина — одним коротким абзацем.

## Что ещё рассматривали

Только если отвергнутые варианты важно помнить.

## Последствия

Только если у решения есть неочевидные последствия.
```

Файл в `main` считается принятым. Если решение изменилось, старый ADR не
переписываем: создаём новый и связываем их ссылкой.
