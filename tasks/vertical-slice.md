# Первый живой вертикальный слайс

Продуктовый контекст: [архитектура живого агента](../ARCHITECTURE.md).

## Сейчас

Виджет работает на подготовленных fixtures. Пользователь видит сценарий Москва →
Санкт-Петербург, но система не вызывает модель, не ходит в Tutu MCP и не строит
результат из реальных данных.

## Что хотим

Пользователь пишет свободный запрос в виджет. Backend запускает реальный
TravelAgent через OpenAI Agents SDK, агент делает реальный вызов Tutu MCP,
возвращает структурированный результат, а виджет получает прогресс и карточки
через SSE.

Минимальный happy path:

```text
Москва → Санкт-Петербург
дата из запроса
реальный Tutu MCP call
реальный model call
2–3 варианта в виджете
короткая рекомендация
```

# Tasks

- [x] TUTU-002 Собрать первый живой вертикальный слайс на pnpm
  Подключить backend, Agents SDK, GPT-5.6, Tutu MCP и SSE так, чтобы виджет
  перестал зависеть только от fixtures хотя бы в одном основном сценарии.

  DoD:
  - проект запускается через `pnpm install` и `pnpm dev`;
  - npm-команды не используются в новых инструкциях;
  - есть backend endpoint `POST /api/travel-runs`;
  - есть SSE endpoint для событий одного `TravelRun`;
  - TravelRun имеет состояния `running`, `completed`, `failed`, а при нехватке
    данных может вернуть `waitingForUser`;
  - используется OpenAI Agents SDK с реальным `OPENAI_API_KEY`;
  - модель задаётся явно как GPT-5.6-вариант, а не default SDK;
  - агент получает короткую инструкцию `travel-agent.prompt.md`;
  - Tutu MCP подключён через `TUTU_MCP_URL=https://mcp.tutu.ru/mcp`;
  - в happy path происходит хотя бы один реальный вызов Tutu MCP;
  - в happy path происходит хотя бы один реальный вызов модели;
  - результат агента валидируется как структурированный `TravelAgentResult`;
  - `difference.compare` считает хотя бы цену и длительность между двумя
    кандидатами;
  - виджет получает минимум три SSE-события: старт, прогресс, итоговое состояние;
  - при ошибке MCP или модели UI показывает понятную ошибку, а не зависает;
  - `pnpm build` проходит;
  - ручная проверка описана в этом файле после выполнения задачи.

  Notes:
  - покупку билета не делать;
  - погоду можно оставить mock/tool stub, если основной сценарий не зависит от
    погодного факта;
  - web search не обязателен для happy path;
  - Codex SDK/App Server не подключать в первом слайсе;
  - `@statelyai/agent` не подключать в основном flow;
  - если XState не успевает, допускается временный простой status store, но это
    нужно явно отметить как debt относительно ADR-004.

  Сделано: Lit-виджет создаёт `TravelRun`, получает продуктовые события через
  SSE и показывает прогресс, карточки, уточнение или понятную ошибку. Backend
  использует XState v6 alpha для lifecycle, одного TravelAgent на GPT-5.6,
  hosted Tutu MCP с единственным разрешённым `search_rail` и детерминированный
  `difference.compare`. Структурированный итог валидируется Zod-схемой; успешный
  run дополнительно проверяет фактические вызовы MCP и difference tool.

  Ручная проверка после настройки `OPENAI_API_KEY`:
  1. Выполнить `pnpm install`, скопировать `.env.example` в `.env` и заполнить ключ.
  2. Запустить `pnpm dev` и открыть `http://127.0.0.1:5173`.
  3. Отправить маршрут Москва → Санкт-Петербург и будущую дату.
  4. Убедиться, что видны старт и прогресс, затем 2–3 реальные карточки и короткая
     рекомендация; в server trace есть model call, `tutu.search_rail` и
     `difference_compare`.
  5. Временно убрать ключ и повторить запрос: UI должен показать понятную ошибку,
     не оставаясь в загрузке.

  - `pnpm build` проходит.

  Сделано: добавлена карта payload-ов для `TripWidgetEvent`, объекты поездки
  приведены к фиксированной форме с явными `null`, лишняя ручная нормализация
  ответа агента удалена. Store отдаёт read-модель через `snapshot`, подписку —
  через отдельный контракт, а XState-переходы используют тип событий машины.
