Продуктовый контекст: [Туту Разница](../PRD.md).

Технический контекст: [архитектура живого агента](../ARCHITECTURE.md),
[правила работы с Tutu MCP](../TUTU_MCP.md) и
[презентационный режим](jury-presentation.md).

## Порядок выполнения

Эта область начинается только после завершения `TUTU-004`. `TUTU-005` —
обязательная завершающая задача перед сдачей проекта жюри: она превращает уже
собранный презентационный режим в публично доступный live-продукт и добавляет
один заметный агентный сценарий обогащения.

## Сейчас

В репозитории есть живой путь Lit → Node API → XState TravelRun → Agents SDK →
Tutu MCP → SSE, но production-контейнер публикует только статический frontend.
Публичный `/api/health` попадает в SPA fallback и возвращает HTML, поэтому режим
«Свой запрос» на production не может запустить агента.

TravelAgent умеет искать железнодорожные варианты через `search_rail` и считать
разницу цены и длительности. Погода, работа городского транспорта и другие
внешние обстоятельства пока не проверяются. Автобусный поиск Tutu MCP описан в
документации проекта, но не разрешён агенту.

## Что хотим

Публичная ссылка сохраняет стабильный сценарий для гарантированной демонстрации
и рядом даёт рабочий режим «Свой запрос». Агент выбирает железнодорожный или
автобусный поиск Tutu по намерению пользователя, а при реальной пользе может
проверить через hosted web search погоду, работу метро или другой городской
контекст и показать, как этот факт меняет практическую ценность маршрута.

Основной финальный поток:

```text
Публичный Lit-виджет
  ↓ POST + SSE через /api
Production Node API
  ↓
XState TravelRun
  ↓
TravelAgent
  ├── Tutu MCP: ровно один search_rail или search_bus
  ├── web search: только релевантный внешний контекст
  └── difference.compare: проверяемая числовая разница
```

# Tasks

- [ ] TUTU-005 Завершить публичный live-контур и контекстное сравнение
  После `TUTU-004` довести production-путь до рабочего состояния и добавить
  контролируемое агентное обогащение, которое заметно влияет на сравнение, но не
  подменяет структурированные данные Tutu результатами веб-поиска.

  DoD:

  **Зависимость и обязательность**

  - задача начинается только после того, как `TUTU-004` отмечена выполненной;
  - `TUTU-005` считается обязательной для финальной готовности проекта, а не
    необязательным улучшением;
  - стабильный сценарный snapshot из `TUTU-004` остаётся доступен независимо от
    сети, API-ключа и состояния внешних сервисов;
  - архитектура одного TravelAgent и XState process manager сохраняется без
    перехода к multi-agent.

  **Production API**

  - production-конфигурация действительно запускает Node API вместе со
    статическим frontend;
  - `/api/*` проксируется в Node API и не попадает в SPA fallback;
  - `/api/health` возвращает JSON от Node API;
  - SSE проходит через production proxy без буферизации и не обрывается раньше
    терминального события TravelRun;
  - `OPENAI_API_KEY` и другие серверные настройки передаются только backend и не
    попадают в frontend bundle или публичный HTML;
  - healthcheck проверяет живой API, а не только наличие главной HTML-страницы;
  - понятная ошибка модели, MCP или web search отображается внутри live-режима и
    не ломает сценарный режим;
  - реальный deploy выполняется только после отдельной команды владельца
    **«выложи»**.

  **Железнодорожный и автобусный поиск**

  - Tutu MCP разрешает минимально необходимые `search_rail` и `search_bus`;
  - агент по запросу пользователя выбирает ровно один основной поиск и не
    вызывает оба инструмента для перестраховки;
  - цены, расписание, перевозчик и доступность вариантов берутся только из Tutu
    MCP, а не из web search;
  - перед вызовом собраны маршрут, дата и вид транспорта; нет probe-запросов,
    параллельных вызовов, автоматических ретраев и перебора дат;
  - проверка завершённого agent run подтверждает фактический вызов выбранного
    Tutu tool и `difference.compare`;
  - нормализация автобусных и железнодорожных кандидатов приводит их к текущему
    `TripWidgetState`, не протаскивая raw MCP payload в UI.

  **Контекст через web search**

  - hosted web search подключён как tool существующего TravelAgent;
  - prompt явно перечисляет допустимые причины вызова: погода на дату поездки,
    работа метро или другого городского транспорта, время события, камера
    хранения и аналогичный факт, способный изменить цену, время или комфорт;
  - web search не вызывается для каждого запроса автоматически и не используется
    для поиска билетов, цен или основного расписания;
  - агент делает не более одного сфокусированного web search за TravelRun;
  - погода проверяется только для даты, для которой доступен осмысленный прогноз;
    дальний прогноз не выдумывается и не выдаётся за факт;
  - факт из веба появляется в карточке только вместе с понятной подписью источника
    или формулировкой, что это оценка;
  - если web search недоступен или не дал надёжного ответа, агент завершает
    сравнение по данным Tutu без придуманного обогащения;
  - числовая разница цены и длительности по-прежнему берётся только из
    `difference.compare`.

  **Демонстрационный эффект**

  - в progress-тексте пользователь видит отдельный смысловой этап проверки
    внешнего контекста, только если tool действительно был вызван;
  - хотя бы один подготовленный live-запрос показывает практическую разницу:
    например дождь при долгом ожидании, закрытое метро после позднего прибытия
    или автобус как более подходящий вид транспорта;
  - UI различает данные Tutu, факт из web search и оценочный вывод агента;
  - рекомендация объясняет, как внешний контекст изменил выбор, а не просто
    пересказывает прогноз или расписание;
  - README, PRD и ARCHITECTURE после реализации описывают фактический production
    flow и границы источников без обещаний отсутствующей функциональности.

  **Границы и проверка**

  - отдельный weather API, покупка билета, checkout, авторизация, persistence и
    multi-agent не добавляются в эту задачу;
  - новые npm-команды не добавляются, используются существующие команды `pnpm`;
  - `pnpm build` и `pnpm exec mdtask validate` проходят;
  - инструкция ручной проверки содержит стабильный сценарий, поезд, автобус,
    контекстный web search, graceful degradation и production health;
  - главный сценарий глазами жюри проверяется только после законченного
    вертикального куска и по явной просьбе владельца;
  - production smoke выполняется только после отдельной команды **«выложи»**.

  Notes:

  - если Tutu MCP отвечает сетевой ошибкой или блокировкой, вызов не повторяется;
  - если до конца доступного времени нельзя надёжно показать внешний факт,
    live-режим остаётся на проверяемых данных Tutu, а сценарный snapshot остаётся
    основным безопасным путём демонстрации;
  - эффект для жюри строится на честном различии источников, а не на количестве
    вызванных tools.
