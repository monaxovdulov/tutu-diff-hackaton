# Презентационный режим для жюри

Продуктовый контекст: [Туту Разница](../PRD.md).

Технический контекст: [архитектура живого агента](../ARCHITECTURE.md) и
[правила работы с Tutu MCP](../TUTU_MCP.md).

## Сейчас

Демо открывает компактный виджет шириной 410 px и показывает десять технических
состояний кнопками `1–10`. У виджета есть `position="inline"`, но нет отдельного
широкого layout-а: inline меняет позиционирование, а не структуру экрана.

Подготовленный сценарий использует вручную заданные цены и расписание. Живой
TravelRun уже умеет получать результат через Agents SDK, Tutu MCP и SSE, но
production-контейнер пока публикует только статический frontend и не проксирует
Node API.

## Что хотим

Одна ссылка должна сразу показывать жюри законченную ценность продукта, а затем
позволять проверить собственный маршрут.

По умолчанию открывается широкий презентационный layout и режим **«Сценарий»**
на смысловом шаге **«Реальная разница»**. Пользователь сразу видит три реальных
варианта, последствия, числовую разницу и рекомендацию. При необходимости он
может пройти сценарий с начала по семантическим шагам.

Вторая вкладка **«Свой запрос»** запускает живой TravelRun через существующий
backend. Компактный встраиваемый виджет остаётся режимом по умолчанию для
обычного использования и не ломается из-за презентационного слоя.

Подготовленный сценарий строится не на придуманных билетах, а на один раз
полученном и сохранённом результате реального вызова `search_rail` Tutu MCP.
Нажатия по шагам не вызывают MCP повторно: презентация воспроизводит сохранённый
snapshot стабильно и без сетевого риска.

## Презентационный сценарий

```text
1. Запрос
2. Варианты
3. Последствия
4. Реальная разница ← стартовый экран
5. Новое условие
6. Рекомендация
```

На стартовом экране:

- выбран режим **«Сценарий»**;
- показаны 2–3 реально найденных варианта;
- крупно показана разница цены, времени и дополнительных последствий;
- источник подписан как сохранённый сценарий с датой получения данных;
- доступны действия **«Показать путь сначала»** и **«Свой запрос»**;
- нет автопрокрутки и технических кнопок `1–10`.

# Tasks

- [x] TUTU-004 Собрать презентационный режим на реальных данных Tutu MCP
  Сделать внутри существующего Lit-виджета широкий презентационный layout,
  подготовить воспроизводимый сценарий из реального MCP-ответа и оставить рядом
  живой режим для собственного запроса.

  DoD:

  **Продуктовое решение**

  - отдельным product ADR зафиксированы два пользовательских режима:
    **«Сценарий»** и **«Свой запрос»**;
  - визуальный layout и источник данных не смешаны в одном параметре: например,
    `layout="compact|presentation"` отвечает за раскладку, а
    `experience="scenario|live"` — за поведение;
  - demo URL без параметров открывает `presentation + scenario` на шаге
    **«Реальная разница»**;
  - компактный режим остаётся обратносуместимым значением по умолчанию для
    публичного API виджета;
  - PRD и README после реализации описывают оба режима и не называют
    сохранённый snapshot живыми данными.

  **Реальные данные и provenance**

  - для будущей даты сделан один осознанный вызов `search_rail` официального
    Tutu MCP по сценарию Москва → Санкт-Петербург;
  - перед вызовом собраны все параметры; нет probe-запросов, параллельных
    вызовов, автоматических ретраев и перебора дат;
  - из ответа выбраны 2–3 действительно найденных и заметно различающихся
    варианта; цены, время и транспортные факты не придуманы и не исправлены под
    заранее желаемый вывод;
  - сохранён минимальный source snapshot, достаточный для проверки
    происхождения данных: tool, параметры поиска, дата получения и использованные
    поля ответа; секреты и ненужный raw payload в frontend не попадают;
  - рядом сохранено нормализованное представление для `TripWidgetState` и
    последовательность презентационных состояний;
  - числовая разница пересчитана детерминированным `difference.compare`, а не
    записана вручную текстом;
  - факты о метро, такси, погоде и событиях имеют собственный источник либо
    явно помечены как оценка; они не выдаются за данные Tutu MCP;
  - UI показывает честную подпись вида **«Данные Tutu · сохранены 19 августа»**,
    а не **«получены сейчас»**;
  - snapshot обновляется только вручную одной pnpm-командой через существующий
    агентный путь; новый npm-script не добавляется.

  **Широкий режим виджета**

  - публичный API и loader поддерживают opt-in презентационный layout;
  - `position="inline"` используется для размещения виджета в потоке страницы,
    а layout отдельно задаёт широкую адаптивную панель;
  - при достаточной ширине три варианта видны рядом, ниже расположен отдельный
    блок **«Реальная разница»** и рекомендация;
  - семантическая навигация показывает шесть продуктовых шагов вместо десяти
    технических snapshot-кнопок;
  - шаги переключаются вручную и восстанавливаются по URL без автопрокрутки;
  - на узком экране presentation layout безопасно складывается в мобильную
    вертикальную раскладку;
  - presentation UI вынесен в небольшие компоненты уровня story rail,
    comparison board и difference summary, а не добавлен одной большой веткой в
    `TutuDiffWidgetElement`;
  - presentation-step и provenance обёрнуты вокруг `TripWidgetState` на уровне
    демо и не расширяют backend-контракт только ради раскладки;
  - существующие карточки, reducer и доменная модель переиспользованы там, где
    они уже подходят.

  **Режим «Свой запрос»**

  - вкладка открывает чистый intake без одновременного дублирования формы и
    нижнего composer-а;
  - запрос запускает существующий путь Node API → XState TravelRun → Agents SDK
    → Tutu MCP → SSE;
  - progress, результат и понятная ошибка остаются внутри того же визуального
    языка;
  - сценарный snapshot и live-session не перезаписывают состояние друг друга
    при переключении вкладок;
  - production-конфигурация готова публиковать Node API и проксировать `/api`,
    а `/api/health` возвращает JSON, а не fallback `index.html`;
  - реальный deploy выполняется только после отдельной команды владельца
    **«выложи»**.

  **Границы и проверка**

  - архитектура TravelAgent, XState, продуктовых SSE-событий и Tutu MCP не
    переписывается ради презентации;
  - покупка билета, авторизация, multi-agent и автоматическое обновление
    snapshot-а не добавляются;
  - `pnpm build` и `pnpm exec mdtask validate` проходят;
  - инструкция ручной проверки содержит отдельно стабильный сценарий и живой
    запрос;
  - главный сценарий глазами жюри проверяется только после законченного
    вертикального куска и по явной просьбе владельца.
